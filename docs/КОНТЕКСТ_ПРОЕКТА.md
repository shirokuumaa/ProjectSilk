## 1. Что за проект

Маркетплейс одежды — по формату как Wildberries, Ozon, Temu, Amazon.

**Отличие от всех конкурентов — примерка.** Три режима:

| Режим | Что делает | Маршрут |
|---|---|---|
| **Try-On Photo** | Загружаешь своё фото → видишь на нём платье | `/tryon/photo` |
| **Try-On Avatar** | Твой аватар по твоим обмерам → надеваешь вещи | `/tryon/avatar` |
| **Try-On AR** | Камера в реальном времени → вещь на тебе | `/tryon/ar` |

**Главная ценность — не фотореализм, а правильный размер.** Ни один
конкурент не говорит покупателю «в талии не хватает 4 см». Мы говорим.
Это решает главную боль онлайн-покупки одежды и главную статью убытков
магазина — возвраты.

Приоритет владельца: **максимум качества по этим трём функциям, невзирая на
сроки и ресурсы.** Сначала три примерки и работающий сайт покупателя, потом
кабинет продавца.

## 3. Архитектура

```
ProjectSilk/
├── client/          React SPA (CRA, react-scripts 5), порт 3000
├── server/          Express + MongoDB Atlas, порт 5050   ← основной бэкенд
├── assistant/       FastAPI: поиск, рекомендации, LGBM-ранжирование
├── fastapi_app/     GPU API (TRELLIS и прочее), порт 8000
├── gpu-infer/       то же, вариант для RunPod
├── scripts/         process_garment.py — конвейер подготовки одежды в Blender
├── seller/          АРХИВ. Не трогать, всё живое в server/
└── docs/            документация, включая этот файл
```

**Запуск (два терминала):**

```bash
# терминал 1
cd ~/ProjectSilk/server && npm install && npm start    # :5050

# терминал 2
cd ~/ProjectSilk/client && npm install && npm start    # :3000
```

Если `npm install` в client ругается на версии — добавь `--legacy-peer-deps`
(React 19 конфликтует с react-scripts 5).

Нужен `server/.env`:
```
PORT=5050
MONGODB_URI=mongodb+srv://…
GPU_URL=http://127.0.0.1:8000
```

## 5. Принятые решения — и от чего отказались

Это самый важный раздел. Если новый ассистент предложит что-то из списка
«отвергнуто» — покажи ему причину, а не обсуждай заново.

### Тело аватара

**Решили:** одна болванка от художника + морф-таргеты (рост, грудь, талия,
бёдра, плечи, полнота). Покупатель вводит четыре числа — тело меняется.
До появления болванки работает процедурное тело из `BodyAvatar.jsx`.

**Отвергли — сканирование тела, фотограмметрия, оценка обмеров по фото.**
Человек вводит обмеры сам, и это **точнее** любой оценки по фотографии.
Ноль инфраструктуры, ноль GPU, ноль ошибок оценки.

**Отвергли — генерацию персонального 3D-тела для каждого покупателя.**
Это GPU на каждого пользователя и мегабайты файлов. Обмеры весят ~200 байт
вместо ~20 МБ и грузятся мгновенно.

### Лицо и волосы

**Решили (20 августа): художник + слайдеры.** 8–10 морфов на лицо (ширина,
челюсть, нос, глаза), 6–8 готовых причёсок цельным мешем с картой
прозрачности, палитра тона кожи. Собирается вручную за минуту. Логика та же,
что с телом: не «похоже на тебя», а «похоже на человека твоего типа».

**Отвергли — Avatar SDK MetaPerson и Avaturn** (селфи → готовая голова с
блендшейпами). Технически лучший вариант, но: селфи уходит на чужой сервер,
платно за каждого аватара, и их тело не подчиняется нашим обмерам.
Возвращаться к этому стоит, только если ручные морфы окажутся слишком грубыми.

**Отвергли — генерацию лица диффузией.** Обсуждали в самом начале. Долго,
дорого на пользователя, попадает в «зловещую долину»: почти-похожее лицо
отталкивает сильнее, чем нейтральное.

**Рассматривали — вообще не делать лицо.** Не отвергнуто окончательно.
Покупатель смотрит на посадку платья, а не на своё лицо. Стоит оставить
переключатель «показать/скрыть голову».

### Реалистичность ткани

**Решили:** три приёма вместе дают ~90% ощущения реализма.
1. **Скиннинг** — вершины платья привязаны к костям тела, вещь двигается как вторая кожа.
2. **Кости подола с пружинами** — цепочка из 4–5 костей в нижней трети платья, у каждой пружина с затуханием. Человек повернулся — подол отстал и качнулся. Так делают плащи и юбки в играх. ~150 строк, держит 60 кадров.
3. **Карты складок** — складки нарисованы в текстуре нормалей, проявляются в местах сгиба. Свет по ним играет, глаз верит.

**Отвергли 18 августа, но пересмотрели 20 августа — настоящую симуляцию ткани (XPBD).**
Первоначальный отказ: в играх её почти не используют, слишком дорого.
**Новое обстоятельство:** WebGPU стал доступен по умолчанию во всех крупных
браузерах, three.js сделал поддержку production-ready. Появились готовые
XPBD-реализации и модуль `three-simplecloth`: красишь вершины скинингового
меша, и эти участки становятся тканью, смешиваясь с обычным скиннингом.
**Текущее решение:** настоящая ткань — на экране аватара; кости с пружинами —
в AR. В AR уже работают MediaPipe и видеопоток, добавлять туда симуляцию
означает драку за GPU, а резких движений в AR почти не бывает.

### Try-On AR

**Решили:** всё считается **в браузере покупателя**. MediaPipe PoseLandmarker
(3D-координаты) для скелета, HandLandmarker для окклюзии руками,
ImageSegmenter для силуэта. Видео никуда не уходит.

**Отвергли — обработку кадров на сервере.** Кадр не успеет слетать на сервер
и обратно 30 раз в секунду. Плюс это видео пользователя на чужой машине.

**Отвергли — диффузионную примерку в AR.** Физически невозможно: одна картинка
около 20 секунд, нужно 30 в секунду. Диффузия остаётся только в режиме «на фото».

**Честный предел.** Без датчика глубины расстояние до человека — всегда оценка.
На резких движениях вещь будет чуть отставать, в плохом свете трекинг начнёт
сбоить. Это ограничение физики, а не кода: обычная камера не измеряет глубину.
Итог будет **убедительным, но не фотореалистичным.** Человек скажет «вау, оно
правда на мне сидит», но не спутает с фотографией. И этого достаточно —
покупку решает правильный размер, которого нет ни у кого.

### Генерация 3D из фото товара

**Решили: TRELLIS.2** (Microsoft, лицензия MIT, вышла в декабре 2025).
4 млрд параметров, разреженное воксельное представление, справляется со
сложной топологией, отдаёт GLB с PBR-текстурами до 4096². Текущий лидер среди
открытых моделей. Запускается разово на арендованном GPU, когда продавец
загружает товар.

**Отвергли — Meshy, Tripo, Rodin Gen-2.5.** Rodin детальнее по геометрии, но
все они хостинговые: кредиты, чужие условия, зависимость от чужого сервиса.
MIT-лицензия TRELLIS.2 означает, что GPU наш и ограничений нет.

**Проблема «платье как бетон» и её решение.** TRELLIS выдаёт **скульптуру** —
треугольники без скелета. Она не может сидеть на теле, потому что не знает
про тело. Лечится **переносом весов скиннинга** в Blender (Data Transfer /
Surface Deform): платье совмещается с болванкой по четырём ориентирам
(плечи, талия), после чего получает скелет и начинает двигаться вместе с телом.
Это и есть «те самые точки через Blender», о которых шла речь раньше.
До появления болванки временно работает `garmentDrape.js` — прижимает ткань
к телу по обмерам прямо в браузере.

**Внутренняя страница проверки обязательна.** Автоматический перенос весов
ошибается примерно на каждой третьей вещи. Нужен внутренний экран: платье на
болванке, четыре точки двигаются мышкой, кнопка «пересчитать».

### Прочее

**Отвергли — ИИ в реальном времени на сервере** для чего бы то ни было в примерке.
Латентность и стоимость на пользователя.

**Одна подготовленная модель обслуживает все три экрана:** просмотр в карточке
товара, аватар в гардеробе, AR через камеру. Поэтому вкладываемся в один
конвейер, а не в три отдельных решения.

## 6. Проблема фронта

**Диагноз:** в проекте **330 инлайновых `style={{…}}`**, 99 обращений к
CSS-модулям и ровно **2** тайлвинд-класса. Tailwind установлен и не используется.

Цвета, радиусы и границы прописаны руками в трёхстах местах. Поэтому сайт
выглядит сшитым из кусков, и перекрасить его целиком кажется невозможным.

**Эталон дизайна:** `projectsilk_v11.html` — сгенерированный макет, к которому
надо привести сайт. Держи файл в `docs/`.

**Хорошая новость:** структура главной уже совпадает с макетом.
В `HomePage.jsx` стоит `TopBar → CategoryMenu → [AvatarPanel | сетка | RightDock]` —
ровно как в v11. Разметку переписывать не надо, надо заменить оформление.

**План переезда:**
1. `client/src/styles/tokens.css` — палитра v11 в CSS-переменных. **Готов**
2. Подключить первой строкой в `index.css`: `@import './styles/tokens.css';`
3. Добавить шрифты в `client/public/index.html` (Inter, Fraunces, JetBrains Mono)
4. Идти по компонентам, заменяя инлайн-стили на `var(--…)`.
   Начинать с `TopBar` и `ProductCardTall` — они дают ~80% визуального эффекта
5. Правило на будущее: **в новом коде никаких хардкодных `#hex`**

Образец правильного оформления — `TryOnAvatar.module.css`, там нет ни одного
хардкодного цвета.

**Палитра v11:** фон `#F2F1EF`, поверхность `#FFFFFF`, границы `#E4E1DC`,
текст `#16141A`, приглушённый `#7A7580`, акцент `#4B3A9E`, вино `#A82742`,
розовый `#F7A8C4`. Пилюли `999px`, карточки `14–18px`.

## 8. Что сделано 20 августа

**`TryOnAvatar.jsx` переписан целиком.** Было: копия AR-камеры; до этого —
черновик со слотами, который требовал сгенерированный на GPU файл аватара
(`avatarFinal` в localStorage) и не показывал одежду вообще.

Стало — работает **без GPU, без художника и без файла аватара**:

1. Тело строится из обмеров через `BodyAvatar`
2. Вещи грузятся как GLB и прижимаются к фигуре через `drapeGarment`
3. Размер считается через `findBestSize`, проблемные зоны подсвечиваются кольцами на фигуре
4. Слоты: платье / верх / низ / верхняя / обувь / аксессуар. Платье и «верх+низ» взаимоисключающие
5. Старые черновики нарядов не теряются — читается прежний формат ключей
6. **У вещи без 3D-модели вердикт по размеру всё равно работает** — он считается из чисел. Страница обязана быть полезной, пока у товаров нет GLB
7. Оформление по токенам v11 — это первая страница в новом дизайне и образец для остальных

**Созданы файлы:**
- `client/src/styles/tokens.css`
- `client/src/pages/tryon/TryOnAvatar.module.css`
- `client/src/pages/tryon/TryOnAvatar.jsx`
- `docs/КОНТЕКСТ_ПРОЕКТА.md` (этот файл)

## 10. От чего зависим

1. **Художник.** Главная зависимость. Техзадание в разделе 11.
2. **GPU на несколько часов** — поднять TRELLIS.2 и прогнать первую партию товаров.
3. **Хранилище для `.glb`.** Сейчас локальная папка `uploads`. Для роста нужно вынести.
4. **Продавцы должны заполнять размерные сетки.** Без них подбор размера —
   наша главная ценность — не работает. Это не техническая задача, а продуктовая:
   заполнение сетки должно быть обязательным при загрузке товара.

## 11. Техническое задание художнику

- Одна болванка, сетка из четырёхугольников, ~15 000 треугольников, поза A
- **Морф-таргеты тела** отдельными формами, 6 штук: рост, обхват груди, талия, бёдра, ширина плеч, полнота
- **Морф-таргеты лица**, 8–10 штук: ширина лица, челюсть, нос, глаза, скулы, губы, брови
- **Причёски**: 6–8 штук, цельным мешем с картой прозрачности, автоподгонка под форму головы, цвет из палитры
- Стандартный humanoid-скелет
- Помеченные вершины-ориентиры: основание шеи, кончики плеч, линия груди, талия, бёдра, колени, уровень пола
- Экспорт в **GLB с морф-таргетами и весами скиннинга внутри файла**
- **Дополнительно и обязательно: 2–3 тестовых платья, привязанных к болванке вручную и правильно.**
  Это эталон, по которому калибруется автоматический перенос весов на этапе 4.
  Без эталона автоматику не настроить

Значения морфов уже считает `BodyProfile.toMorphTargets()` на сервере —
болванка должна принимать их в диапазоне 0…1, где 0.5 = среднее телосложение.

## 12. Чего ждать по качеству — честно

**Будет отлично:** посадка по реальным обмерам, вердикт по размеру, поворот
вещи вместе с человеком, колыхание подола, скрытие за руками, вид сзади при
развороте, складки в местах сгиба.

**Будет приблизительно:** тело — оценка по четырём числам, а не скан.
Освещение вещи подгоняется под кадр примерно, а не рассчитывается физически.
Нарисованные складки появятся в правильных местах, но не отреагируют на
конкретное движение.

**Не будет:** фотореализма, неотличимого от фотографии. См. «честный предел»
в разделе 5.

Это не повод снижать планку — это повод не тратить месяцы на последние 5%,
пока не сделаны первые 90%.
